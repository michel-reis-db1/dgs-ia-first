# Dev Ex. 3.1 — Entregável 3: Code review e correções

> Simulando o passo pedido no enunciado ("faça o code review do que o Copilot gerou"): estes são os dois problemas reais que uma primeira versão gerada sem revisão teria, e como a versão final (`dev-3.1-schema-zod.md` + `dev-3.1-response-validator.md`) os resolve.

**Achado #1 — schema aceitava campos extras.** Uma primeira versão razoável do schema (`z.object({...})` sem `.strict()`) passa no `safeParse` mesmo se o modelo devolver campos além do contrato (ex: um `debug_info` ou um `raw_chunks` que o prompt não deveria estar vazando). Sem `.strict()`, esse vazamento não gera nenhum sinal — silenciosamente aceito. **Correção:** `.strict()` adicionado; coberto pelo teste "rejeita campos extras fora do contrato".

**Achado #2 — guardrail de conteúdo rodando sobre o payload bruto.** Uma implementação ingênua tende a escrever a regex contra `raw` (ou contra `JSON.stringify(raw)`) para "economizar" o parse, antes de saber se o schema é válido. Isso quebra a garantia de tipo (o `answer` pode não ser string, pode estar aninhado diferente) e pode gerar falso-negativo se o modelo devolver a resposta num formato ligeiramente distinto do esperado. **Correção:** o guardrail 2 só roda depois do `safeParse` ter sucesso, sobre `parsed.data.answer` — já garantidamente uma string.

**Risco residual (não "corrigido", documentado):** o guardrail 2 é um heurístico de palavras-chave, não uma verificação semântica. Uma resposta do tipo *"geralmente não recomendamos, mas tecnicamente é possível devolver carga perigosa mediante autorização"* contém a palavra "não" e passaria pelo `NEGATION_PATTERN` mesmo afirmando a possibilidade no fim — um falso-negativo real. Regex por si só não resolve isso; a mitigação correta é em camadas (Delivery Manager Ex. 3.1): reforçar no system prompt, e rotear para HITL qualquer resposta com `confidence_score` abaixo de um limiar quando o tema é carga perigosa, em vez de confiar 100% no regex. Vale registrar esse limite explicitamente para quem for usar este módulo — é a diferença entre "guardrail determinístico" e "guardrail infalível".
